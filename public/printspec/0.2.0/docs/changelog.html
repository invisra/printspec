Changelog

0.4.0

Feature:

  • OpenSCAD generator: implement whole-part chamfer for the round_spacer and spacer_block part families (honoring chamfer.distance). round_spacer uses a rotate_extrude chamfered profile; spacer_block uses a hull() of inset/full cross-sections. A targeted chamfer (chamfer.target set), fillet, and chamfers on the other families still report the existing "requested but not implemented" warning, and CadQuery is unchanged. The Python and TypeScript OpenSCAD generators emit identical output, enforced by the generator parity test.

  • OpenSCAD generator: implement whole-part fillet for round_spacer (honoring fillet.radius) via a rotate_extrude arc profile whose points are emitted as symbolic OpenSCAD (sin/cos evaluated at render time), keeping the Python and TypeScript output byte-identical. Chamfer takes precedence when both are requested. Targeted fillets and fillets on the other families still warn; box-edge fillet (spacer_block) is deferred because it is not cleanly expressible in dependency-free OpenSCAD.

  • OpenSCAD generator: implement whole-part chamfer and fillet for rounded_rectangular_plate. The plate is built as a hull() of corner columns, so each corner cylinder is swapped for a chamfered/filleted rotate_extrude disc (radius = corner_radius), and the hull finishes the whole plate perimeter uniformly. CadQuery is unchanged.

  • OpenSCAD generator: implement chamfer and fillet for electronics_standoff, including based (stepped) standoffs. A base-less standoff finishes its outer top/bottom edges like round_spacer; a based standoff finishes its two exposed extremes — top finishes the shaft top edge, bottom the base bottom edge, and whole-part finishes both (the internal base/shaft joint stays square). The chamfer/fillet solid helpers gained an optional height-expression argument so the base sub-cylinder (base_height) can reuse them; existing callers are unchanged and byte-identical.

  • OpenSCAD generator: implement fillet for spacer_block, completing chamfer + fillet across all three finish-capable families. Box-edge fillet is built as a hull() of thin cross-section slices whose inset follows the fillet arc (symbolic sin/cos, same [0:8] sampling as the round profiles), and honors the whole-part / top / bottom targeting. Byte-identical across the Python and TypeScript packages.

  • OpenSCAD generator: support targeted top and bottom finishes. chamfer.target / fillet.target values "top" and "bottom" now finish only that edge for the implemented families (round_spacer, spacer_block chamfer, rounded_rectangular_plate); an omitted target still means whole-part, and any other target value is still reported as not implemented. No schema change — target remains a free string, so this is fully backward-compatible. The chamfer/fillet profile and box-body generators were factored into shared, edge-parameterized helpers kept byte-identical across the Python and TypeScript packages.

  • OpenSCAD generator: implement chamfer and fillet for drawer_divider. A divider is a thin box (length × thickness × height) with notches cut from the top, so it reuses the spacer_block box-body helpers — now parameterized on their cross-section dimension names so the divider can pass thickness as the second dimension — and subtracts the notches from the finished box. Honors whole-part / top / bottom targeting; the no-finish output is byte-identical to before. The drawer-divider schema gains optional chamfer/fillet finishing properties (mirroring spacer_block), and CadQuery/brepjs still warn that the request isn't implemented for this family.

  • OpenSCAD generator: implement chamfer and fillet for cable_comb. A comb is a flat plate (length × width × thickness) with slots cut into one long edge, so it reuses the same box-body helpers and subtracts the slots from the finished plate, honoring whole-part / top / bottom targeting; the cable_comb schema already carried the finishing properties. Also fixes a latent cross-language divergence: the Python generator wrapped cable_comb dimensions in float() and emitted 70.0 where the TypeScript generator emitted 70, so the two OpenSCAD outputs were not byte-identical for this family. A shared _num() formatter now matches JavaScript's Number.toString() (IEEE-754 shortest round-trip, no trailing .0), making the no-finish and finished output byte-identical across both packages. Geometry is unchanged (OpenSCAD treats 70 and 70.0 identically).

  • OpenSCAD generator: implement chamfer and fillet for cable_clip, restricted to a bottom target. The clip is a base plate (base_length × width × thickness) with a cable arch bridged over it, so the base plate's bottom outer edge is its one closed, solid perimeter clear of the arch; only a bottom target builds (the base cube becomes a bottom-finished box body of height thickness), leaving the arch bridge, cable channel and mount holes unchanged and preserving the existing "arch is approximated" warning, while whole-part and top requests still warn. The cable_clip schema already carried the finishing properties; the no-finish output is unchanged and byte-identical across the Python and TypeScript packages.

  • OpenSCAD generator: implement chamfer and fillet for wall_mount_bracket, restricted to a top target. The bracket is a vertical back plate (width × thickness × height) with a horizontal foot tab at its base, so the plate's top edge is its one closed, solid perimeter away from the tab; only a top target builds (the plate cube becomes a top-finished box body), leaving the tab and screw holes unchanged, while whole-part and bottom requests still warn. The wall-mount-bracket schema gains optional chamfer/fillet finishing properties; the no-finish output is unchanged and byte-identical across the Python and TypeScript packages.

  • OpenSCAD generator: implement chamfer and fillet for project_enclosure_tray, restricted to a bottom target. A tray's only closed, solid perimeter is the floor's outer bottom edge (the top is an open wall rim, not a face), so only a bottom target builds: the floor cube is swapped for a box-body finished on its bottom edge (height = floor_thickness), leaving the four walls and the mount holes unchanged; whole-part and top requests still warn. The box-body helpers gained an optional height-expression argument (like the solid helpers already had) so the floor sub-box can reuse them; existing callers pass the default height and are byte-identical. The project-enclosure-tray schema gains optional chamfer/fillet finishing properties, and the no-finish output is unchanged.

Security hardening (composable-part validation):

  • Restrict a text feature's fontUrl to an inert data: URI or https on a small allowlist of trusted font hosts (fonts.gstatic.com); reject http:// and every other scheme/host. fontUrl is fetched at brepjs kernel runtime by loadFont() -> fetch(), so an unrestricted host was a server-side request forgery (SSRF) vector (cloud metadata / internal endpoints). Extend the allowlist deliberately.
  • Bound composable-part geometric complexity to prevent a schema-valid denial-of-service: add schema maxItems (components 200, features 400, groups 100) and a semantic ceiling on total pattern-expanded instances (20,000, conservatively over-estimated by the largest group pattern), since a single 100x100 rectangular pattern already expands to 10,000 solid instances. Add maxLength: 256 to text content.
  • Enforced in both semantic.ts and semantic.py (kept in parity) and in the schema (synced to all destinations and the regenerated schema validator).

npm package version:

The schema version track stays at 0.2.0 (root package.json / packages/python/pyproject.toml) -- these are additive constraints within schema 0.2.0, not a new schema version, so the pinned // Generated by printspec 0.2.0 contract and every $id are unchanged.   • Add swept_profile as a new composable-part component kind: dimensions: {profile, path}, where profile is an extruded_profile-style array of {x, y} vertices (including curve support) and path is an array of 2 or more {x, y, z} points connected by straight lines, swept via brepjs's real sweep(profileWire, spineWire, options?) operation -- unlocking cable channels, handles, bent standoffs, and any other shape that follows a path none of the other component kinds approximate directly. Unlike every other feature, thread takes no size parameter of its own for the ridge's radius: it's always derived directly from the target's own dimensions (a cylinder/boss's diameter, a tube's outerDiameter/innerDiameter, or a stacked hole feature's own diameter for an internal thread -- the same stacking convention counterbore/countersink already use), so the thread always sits exactly flush with the surface it belongs to, with no way to author a mismatched radius. It also found the ridge extends a small amount (a few percent of its own volume) past both ends of its nominal [0, height] range, an inherent characteristic of thread()'s own lofted tooth-section construction rather than a generator bug -- harmless in practice (still real-kernel-verified valid), documented rather than worked around.   • Add loft_profile as a new composable-part component kind: dimensions: {profiles}, where profiles is an array of 2 or more {points, z} cross-sections, blended via brepjs's real loft(wires: Wire[], options?) operation -- unlocking square-to-round adapters, tapered housings, and any other transitional shape none of the other component kinds approximate directly. Each section's points is the same extruded_profile-style vertex array (including the curved-segment curve support added alongside this), built into a closed wireLoop via the same shared buildProfileEdges(); confirmed brepjs's loft() already returns a capped, valid Solid directly with no separate end-capping step needed. Each section is centered on its own local XY origin independently -- deliberately not on one shared bounding box across sections -- so concentric stacking is the default; every section's z is shifted uniformly so the whole component's base still lands at the component's own Z=0, matching every other kind's convention. brepjs's loft() handles mismatched vertex counts between sections (a 4-point square lofting into a 6-point hexagon, for instance) by corresponding vertices automatically, so sections aren't required to share a point count. Has a real derived AABB (the widest hx/hy across all sections, the full Z span for height) and so participates fully in relation anchoring and the connectivity check, the same as extruded_profile/revolved_profile; excluded (like ellipsoid/revolved_profile) from hole/slot footprint/depth bounds-checking and from shell/fillet/chamfer support, since it has no single footprint number and no flat cap or straight edge for either technique to reliably find. Added examples/composable/square-to-round-duct-adapter.json (a classic HVAC-style transition adapter, its round profile itself built from 4 quarter-circle arcs via curve, combining both new capabilities), real-kernel-verified as a valid solid with a plausible volume -- unlike every other kind added this session, a square-to-round loft has no simple closed-form volume formula to check exactly against, so validity and dimensional plausibility (not an exact hand-derived match) is the appropriate bar here.

  • Add curved segments to extruded_profile and revolved_profile: any point in points may set an optional curve ({type: "arc", through} or {type: "bezier", controlPoints: [...]}) to make the edge to the next point an arc (brepjs's threePointArc(start, through, end)) or a Bezier curve (brepjs's bezier([start, ...controlPoints, end])) instead of a straight line, for either kind's own coordinate convention ({x, y} for extruded_profile, {radius, z} for revolved_profile). Both kinds share one buildProfileEdges() implementation (parameterized only by the coordinate shift and 3D-point-string convention each already had), and both pointsBoundingBox()/revolveProfileExtents() now include every curve's through/controlPoints in the bounding box (via a shared allProfileCoordinatePairs()), not just the main vertices -- an arc bulge or Bezier control point can extend well beyond the polygon the vertices alone would form, which would otherwise silently produce a too-small footprint for centering, relation anchoring, and the connectivity check. Real-kernel-verified for both curve types: threePointArc's bulge area matches a hand-derived semicircle-segment area exactly, and bezier's matches the standard quadratic-Bezier area-vs-chord formula (2/3 of the control triangle's area) exactly. Also caught and documented a real authoring hazard specific to revolved_profile: an aggressively-chosen through/control point (rather than one near the curve's own natural midpoint relative to its immediate neighbors) can produce a profile that fails outright at brepjs's revolve() step (REVOLVE_FAILED) instead of merely an unintended shape, confirmed while authoring one of the two new worked examples below and fixed by choosing a more localized through point. Added examples/composable/rounded-corner-bracket-with-arc-profile.json (a bracket footprint with one corner rounded via curve instead of a separate fillet feature) and examples/composable/flared-hub-with-curved-revolve-profile.json (a hub that flares via an arc instead of a sharp step), both real-kernel-verified to match their hand-derived volumes exactly.
